Part 2: Generated Machine Code - Instruction Scheduling and Multiply-Add Fusion
==================================================================
Loop: sobel_row_ptr() column loop (memory_pipelines.cpp)
Build A: -O0                                                outputs/asm/memory_pipelines_O0.s, lines 604-635
Build B: -O3 -fno-tree-loop-vectorize -fno-tree-slp-vectorize   outputs/asm/memory_pipelines_O3_novec.s, lines 471-517

What changed
------------
At -O0 instructions come out in source order, one statement at a time: load pixel, build the
Gx address, load Gx, multiply, load x_acc, add, store x_acc, then the same again for Gy.
Each step needs the result of the one before it, so the core waits on every load.

-O0, one tap of x_acc in source order (lines 616-620):

    ldrsb   w0, [x0]            // Gx[a][b]
    mul     w0, w2, w0          // waits for the load
    ldr     w1, [sp, 124]       // x_acc
    add     w0, w1, w0          // waits for both
    str     w0, [sp, 124]

At -O3, with the loops unrolled, the compiler has 27 independent loads and 18
multiply-accumulates to arrange. It interleaves them so loads for later taps are already in
flight while earlier multiplies run. The Gx (x_acc) and Gy (y_acc) chains are also
interleaved with each other, so the Cortex-A76's out-of-order core always has work ready. Each
"multiply, then add to the accumulator" pair also becomes one madd instruction
(dst = a*b + acc).

-O3, interleaved loads and the two accumulator chains (lines 471-496):

    ldrb    w7, [x21, 1]        // pixel load
    ldrsb   w0, [x19, 1]        // Gy coefficient
    ldrsb   w5, [x20, 1]        // Gx coefficient
    ldrb    w9, [x21]           // next pixel, already loading
    ldrsb   w6, [x19]
    ldrb    w8, [x21, 2]
    mul     w0, w0, w7          // Gy chain starts
    ldrsb   w2, [x19, 2]
    mul     w5, w5, w7          // Gx chain starts
    ldrsb   w1, [x20]
    ldrb    w11, [x23]          // loads for the next row of the kernel
    madd    w6, w6, w9, w0      // Gy += pixel * coeff, one instruction
    ldrsb   w7, [x19, 3]
    ldrsb   w0, [x20, 2]
    madd    w2, w2, w8, w6      // Gy chain
    madd    w1, w1, w9, w5      // Gx chain, independent of the Gy chain
    ...
    madd    w7, w7, w11, w2
    madd    w0, w0, w8, w1

The column loop is also rotated: its test is at the bottom (cmp x21, x25 / bne .L60) rather
than jumping to a separate condition block every iteration, as -O0 does (b .L41, lines 584,
661-666).

How it helps performance
------------------------
madd halves the number of arithmetic instructions for the 18 taps (18 instead of 36). The
scheduling hides the 4-cycle L1 load-to-use latency behind other independent work instead of
stalling after every load. Keeping two independent accumulator chains in flight lets the A76
issue Gx and Gy work in the same cycles.

Measured check (1920x1080, 2.4 GHz): Sobel went from 83.7 ns = ~201 cycles per pixel at -O0 to
9.7 ns = ~23 cycles per pixel at -O3 (8.6x). The instruction count fell from ~511 to 60 per pixel
(8.5x), so instructions per cycle stayed about the same (~2.5). Almost all of the speedup comes
from executing fewer instructions. Scheduling is what keeps the much denser -O3 code (no easy
stack loads/stores to fill the pipeline) running at that same rate instead of stalling on
load latency.
